다른 개발자가 사용할 모듈을 개발할 때, 해당 모듈을 사용하는 개발자에게 신뢰할 수 있고 일관된 경험을 제공하도록 돕는 워크플로를 따를 수 있습니다. 이 주제에서는 해당 워크플로의 상위 수준 단계들을 설명합니다.

모듈 개발에 대한 개요는 [Developing and publishing modules](developing)를 참조하십시오.

**함께 보기**

* 단순히 코드에서 외부 패키지를 사용하려는 것이라면, [의존성 관리](/doc/modules/managing-dependencies)를 확인하십시오.
* 새로운 버전이 출시될 때마다, 모듈의 버전 번호를 통해 변경 사항을 알립니다. 자세한 내용은 [모듈 버전 번호 매기기](/doc/modules/version-numbers)를 참조하십시오.

## 공통 워크플로우 단계 {#common-steps}

다음 시퀀스는 예시로 든 새로운 모듈의 릴리스 및 버전 관리 워크플로우 단계를 보여줍니다. 각 단계에 대한 자세한 내용은 본 주제의 섹션을 참조하십시오.

1. **모듈을 시작**하고 소스를 구성하여 개발자가 사용하기 쉽고 유지보수하기 편리하게 만드십시오.

모듈 개발이 처음이시라면, [튜토리얼: Go 모듈 생성하기](/doc/tutorial/create-module)를 확인해 보세요.

Go의 분산형 모듈 배포 시스템에서는 코드를 어떻게 구성하느냐가 중요합니다. 자세한 내용은 [Managing module source](/doc/modules/managing-source)를 참조하십시오.

1.  게시되지 않은 모듈의 함수를 호출하는 **로컬 클라이언트 코드를 작성**하도록 설정합니다.

모듈을 게시하기 전에는 `go get`과 같은 명령어를 사용하는 일반적인 의존성 관리 워크플로를 통해 사용할 수 없습니다. 이 단계에서 모듈 코드를 테스트하는 좋은 방법은 호출하는 코드와 동일한 로컬 디렉토리에 모듈을 두고 시도하는 것입니다.

로컬 개발에 대한 자세한 내용은 [게시되지 않은 모듈을 대상으로 코딩하기](#unpublished)를 참조하세요.

1.  모듈의 코드가 다른 개발자들이 테스트해 볼 준비가 되면, 알파(alpha) 및 베타(beta)와 같은 **v0 프리릴리스(pre-release) 배포를 시작하세요**. 자세한 내용은 [프리릴리스 버전 배포하기](#pre-release)를 참조하십시오.

1.  안정성이 보장되지는 않지만 사용자가 시도해 볼 수 있는 **v0를 출시**하십시오. 자세한 내용은 [첫 번째(불안정한) 버전 게시하기](#first-unstable)를 참조하십시오.

1.  v0 버전이 게시된 후에도 계속해서 **새 버전을 릴리스**할 수 있으며, 그렇게 해야 합니다!

이 새로운 버전들에는 버그 수정(패치 릴리스), 모듈의 공개 API 추가(마이너 릴리스), 그리고 브레이킹 변경 사항(breaking changes)이 포함될 수 있습니다. v0 릴리스는 안정성이나 하위 호환성을 보장하지 않으므로, 해당 버전들에서는 브레이킹 변경 사항을 적용할 수 있습니다.

더 자세한 내용은 [버그 수정 게시](#bug-fixes) 및 [파괴적이지 않은 API 변경 사항 게시](#non-breaking)를 참조하세요.

1.  안정 버전을 출시할 준비가 되면, **사전 릴리스를 알파 및 베타 버전으로 게시**합니다. 자세한 내용은 [사전 릴리스 버전 게시](#pre-release)를 참조하세요.

1. **첫 번째 안정 버전**으로 v1을 릴리스합니다.

이 릴리스는 모듈의 안정성에 대한 약속을 제공하는 첫 번째 릴리스입니다. 자세한 내용은 [첫 번째 안정 버전 게시하기](#first-stable)를 참조하십시오.

1.  v1 버전에서는 **버그 수정을 계속 진행**하고, 필요한 경우 모듈의 public API에 내용을 추가하십시오.

자세한 내용은 [버그 수정 게시](#bug-fixes) 및 [파괴적이지 않은 API 변경 사항 게시](#non-breaking)를 참조하세요.

1. 피할 수 없는 경우, breaking changes는 **새로운 메이저 버전(major version)**에서 배포하십시오.

메이저 버전 업데이트(예: v1.x.x에서 v2.x.x로의 업데이트)는 모듈 사용자에게 매우 파괴적인 업그레이드가 될 수 있습니다. 이는 최후의 수단이어야 합니다. 자세한 내용은 [Breaking API 변경 사항 게시하기](#breaking)를 참조하세요.

## 게시되지 않은 모듈을 대상으로 코딩하기 {#unpublished}

모듈이나 모듈의 새 버전을 개발하기 시작할 때는 아직 이를 게시(publish)하지 않은 상태일 것입니다. 모듈을 게시하기 전까지는 Go 명령어를 사용하여 해당 모듈을 의존성으로 추가할 수 없습니다. 대신, 초기에는 게시되지 않은 모듈의 함수를 호출하는 다른 모듈에서 클라이언트 코드를 작성할 때, 로컬 파일 시스템에 있는 모듈의 복사본을 참조해야 합니다.

클라이언트 모듈의 `go.mod` 파일에서 `replace` 지시어를 사용하면 모듈을 로컬에서 참조할 수 있습니다. 자세한 내용은 [로컬 디렉터리의 모듈 코드 요구(Requiring module code in a local directory)](managing-dependencies#local_directory)를 참조하십시오.

## 프리릴리스 버전 게시하기 {#pre-release}

다른 사용자들이 모듈을 미리 사용해 보고 피드백을 줄 수 있도록 프리릴리스(pre-release) 버전을 게시할 수 있습니다. 프리릴리스 버전은 안정성을 보장하지 않습니다.

사전 릴리스 버전 번호에는 사전 릴리스 식별자가 추가됩니다. 버전 번호에 대한 자세한 내용은 [Module version numbering](/doc/modules/version-numbers)을 참조하십시오.

다음은 두 가지 예시입니다:

```
v0.2.1-beta.1
v1.2.3-alpha
```

사전 릴리스(pre-release)를 제공할 때, 사전 릴리스를 사용하는 개발자는 `go get` 명령어를 통해 버전을 명시적으로 지정해야 한다는 점을 유의하세요. 기본적으로 `go` 명령어는 요청한 모듈을 찾을 때 사전 릴리스 버전보다 정식 릴리스 버전을 우선시하기 때문입니다. 따라서 개발자는 다음 예시와 같이 사전 릴리스 버전을 명시적으로 지정하여 가져와야 합니다.

```
go get example.com/theirmodule@v1.2.3-alpha
```

저장소의 모듈 코드에 태그를 지정하고, 태그에 프리릴리스(pre-release) 식별자를 명시하여 프리릴리스 버전을 게시할 수 있습니다. 자세한 내용은 [모듈 게시하기](publishing)를 참조하세요.

## 첫 번째 (unstable) 버전 게시하기 {#first-unstable}

pre-release 버전을 게시할 때와 마찬가지로, 안정성이나 하위 호환성을 보장하지는 않지만 사용자가 모듈을 미리 체험해 보고 피드백을 제공할 수 있는 릴리스 버전을 게시할 수 있습니다.

불안정 릴리스(Unstable releases)는 버전 번호가 v0.x.x 범위에 있는 릴리스를 말합니다. v0 버전은 안정성이나 하위 호환성을 보장하지 않습니다. 하지만 v1 및 그 이후 버전으로 안정성 약속을 하기 전에, 피드백을 받고 API를 다듬을 수 있는 방법을 제공합니다. 자세한 내용은 [Module version numbering](version-numbers)을 참조하십시오.

다른 공개 버전과 마찬가지로, 안정적인 v1 버전을 출시하기 위해 변경 사항을 적용함에 따라 v0 버전 번호의 마이너(minor) 및 패치(patch) 부분을 증가시킬 수 있습니다. 예를 들어, v0.0.0을 출시한 후 첫 번째 버그 수정 세트가 포함된 v0.0.1을 출시할 수 있습니다.

다음은 버전 번호의 예시입니다:

```
v0.1.3
```

저장소의 모듈 코드에 태그를 지정하고, 태그에 `v0` 버전 번호를 명시하여 불안정한(unstable) 릴리스를 게시할 수 있습니다. 자세한 내용은 [모듈 게시하기](publishing)를 참조하세요.

## 첫 번째 안정 버전 게시하기 {#first-stable}

첫 번째 안정 버전(stable release)은 v1.x.x 버전 번호를 갖게 됩니다. 첫 번째 안정 버전은 피드백을 받고, 버그를 수정하며, 사용자를 위해 모듈을 안정화한 프리릴리스(pre-release) 및 v0 릴리스 이후에 출시됩니다.

v1 릴리스를 통해, 귀하는 모듈을 사용하는 개발자들에게 다음과 같은 사항을 약속하게 됩니다:

* 사용자는 자신의 코드를 수정하지 않고도 메이저 버전의 이후 마이너 및 패치 릴리스로 업그레이드할 수 있습니다.
* 함수 및 메서드 시그니처를 포함하여, 하위 호환성을 깨뜨리는 모듈의 public API 변경을 더 이상 수행하지 않습니다.
* 하위 호환성을 깨뜨리는 exported type의 제거를 수행하지 않습니다.
* API에 대한 향후 변경 사항(예: struct에 새 필드 추가)은 하위 호환성을 유지하며, 새로운 마이너 릴리스에 포함됩니다.
* 버그 수정(예: 보안 수정)은 패치 릴리스에 포함되거나 마이너 릴리스의 일부로 포함됩니다.

**참고:** 첫 번째 메이저 버전이 v0 릴리스일 수 있지만, v0 버전은 안정성이나 하위 호환성 보장을 의미하지 않습니다. 결과적으로, v0에서 v1으로 업데이트할 때는 v0 릴리스가 안정적인 버전으로 간주되지 않았으므로 하위 호환성을 깨뜨리는 변경 사항에 대해 크게 신경 쓸 필요가 없습니다.

버전 번호에 대한 자세한 내용은 [모듈 버전 번호 매기기](/doc/modules/version-numbers)를 참조하십시오.

다음은 안정 버전 번호의 예시입니다:

```
v1.0.0
```

저장소에서 모듈 코드에 태그를 지정하고, 태그에 `v1` 버전 번호를 명시하여 첫 번째 안정화 릴리스(stable release)를 게시합니다. 자세한 내용은 [모듈 게시하기](publishing)를 참조하세요.

## 버그 수정 게시 {#bug-fixes}

변경 사항이 버그 수정으로만 제한된 릴리스를 게시할 수 있습니다. 이를 패치 릴리스(patch release)라고 합니다.

_패치 릴리스(patch release)_는 사소한 변경 사항만을 포함합니다. 특히, 모듈의 public API에 대한 변경 사항은 포함되지 않습니다. 해당 코드를 사용하는 개발자는 자신의 코드를 수정할 필요 없이 안전하게 이 버전으로 업그레이드할 수 있습니다.

**참고:** 패치 릴리스 시 해당 모듈의 전이적 의존성(transitive dependencies)을 패치 버전 이상으로 업그레이드하지 않도록 주의하십시오. 그렇지 않으면 사용자가 모듈의 패치 버전을 업그레이드할 때, 사용 중인 전이적 의존성에 의도치 않게 더 파괴적인 변경 사항이 포함될 수 있습니다.

패치 릴리스는 모듈 버전 번호의 패치 부분을 증가시킵니다. 자세한 내용은 [모듈 버전 번호 지정](/doc/modules/version-numbers)을 참조하십시오.

다음 예시에서 v1.0.1은 패치 릴리스(patch release)입니다.

이전 버전: `v1.0.0`

새 버전: `v1.0.1`

저장소의 모듈 코드에 태그를 지정하고, 태그의 패치 버전 번호를 증가시켜 패치 릴리스를 게시합니다. 자세한 내용은 [모듈 게시하기](publishing)를 참조하세요.

## 하위 호환성을 유지하는 API 변경 사항 게시 {#non-breaking}

모듈의 공개 API에 하위 호환성을 유지하는 변경 사항(non-breaking changes)을 적용하고, 이를 _minor_ 버전 릴리스로 배포할 수 있습니다.

이 버전은 API를 변경하지만, 호출 코드를 망가뜨리는 방식은 아닙니다. 여기에는 모듈 자체의 종속성 변경이나 새로운 함수, 메서드, 구조체 필드 또는 타입의 추가가 포함될 수 있습니다. 이러한 변경 사항이 포함되더라도, 이와 같은 릴리스는 모듈의 함수를 호출하는 기존 코드에 대해 하위 호환성과 안정성을 보장합니다.

마이너 릴리스는 모듈 버전 번호의 마이너 부분을 증가시킵니다. 자세한 내용은 [Module version numbering](/doc/modules/version-numbers)을 참조하십시오.

다음 예시에서 v1.1.0은 마이너 릴리스(minor release)입니다.

이전 버전: `v1.0.1`

새 버전: `v1.1.0`

저장소의 모듈 코드에 태그를 지정하고 태그의 마이너 버전 번호를 올림으로써 마이너 릴리스를 게시할 수 있습니다. 자세한 내용은 [모듈 게시하기](publishing)를 참조하세요.

## 파괴적 API 변경 사항 게시 {#breaking}

하위 호환성을 깨뜨리는 버전을 배포하려면 _major_ 버전 릴리스를 배포하면 됩니다.

주 버전(major version) 릴리스는 하위 호환성을 보장하지 않으며, 이는 일반적으로 해당 모듈의 이전 버전을 사용하는 코드를 중단시킬 수 있는 공개 API의 변경 사항이 포함되어 있기 때문입니다.

메이저 버전 업그레이드가 해당 모듈에 의존하는 코드에 미칠 수 있는 파괴적인 영향을 고려하여, 가능하다면 메이저 버전 업데이트를 피해야 합니다. 메이저 버전 업데이트에 대한 자세한 내용은 [Developing a major version update](/doc/modules/major-version)를 참조하십시오. 하위 호환성을 깨뜨리는 변경(breaking changes)을 피하는 전략에 대해서는 블로그 포스트 [Keeping your modules compatible](/blog/module-compatibility)를 참조하십시오.

다른 종류의 버전을 게시할 때는 기본적으로 모듈 코드에 버전 번호 태그를 지정하기만 하면 되지만, 메이저 버전 업데이트를 게시하려면 더 많은 단계가 필요합니다.

1. 새로운 메이저 버전의 개발을 시작하기 전, 저장소(repository)에 새 버전의 소스 코드가 들어갈 위치를 생성하세요.

이를 수행하는 한 가지 방법은 새로운 메이저 버전과 그 이후의 마이너 및 패치 버전을 위해 저장소에 별도의 새 브랜치를 생성하는 것입니다. 자세한 내용은 [Managing module source](/doc/modules/managing-source)를 참조하십시오.

1. 모듈의 `go.mod` 파일에서 다음 예시와 같이 새 메이저 버전 번호를 추가하여 모듈 경로를 수정하십시오.

```
    example.com/mymodule/v2
    ```

모듈 경로가 모듈의 식별자라는 점을 고려하면, 이 변경 사항은 결과적으로 새로운 모듈을 생성하는 것과 같습니다. 또한 패키지 경로를 변경함으로써, 개발자가 의도치 않게 자신의 코드를 망가뜨리는 버전을 임포트하지 않도록 보장합니다. 대신, 업그레이드를 원하는 사용자는 기존 경로를 새 경로로 명시적으로 교체하게 됩니다.

1.  코드에서 업데이트 중인 모듈 내의 패키지를 임포트하는 모든 패키지 경로를 변경하십시오. 여기에는 업데이트 중인 모듈 자체에 포함된 패키지도 포함됩니다. 모듈 경로를 변경했기 때문에 이 작업이 필요합니다.

1.  다른 새로운 릴리스와 마찬가지로, 공식 릴리스를 게시하기 전에 피드백과 버그 보고서를 받기 위해 프리릴리스(pre-release) 버전을 게시해야 합니다.

1. 리포지토리에서 모듈 코드에 태그를 지정하여 새로운 메이저 버전을 게시하십시오. 이때 태그의 메이저 버전 번호를 증가시켜야 합니다. (예: v1.5.2에서 v2.0.0으로 변경)

더 자세한 내용은 [모듈 게시하기](/doc/modules/publishing)를 참조하십시오.
