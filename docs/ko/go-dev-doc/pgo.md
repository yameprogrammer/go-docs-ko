# 개요 {#overview}

피드백 기반 최적화(FDO)로도 알려진 프로파일 가이드 최적화(PGO)는 애플리케이션의 대표적인 실행 결과에서 얻은 정보(프로파일)를 다음 빌드 시 컴파일러에 다시 제공하는 컴파일러 최적화 기법입니다. 컴파일러는 이 정보를 사용하여 더 정확한 최적화 결정을 내립니다.

예를 들어, 컴파일러는 프로파일을 통해 빈번하게 호출되는 것으로 나타난 함수를 더 공격적으로 인라이닝(inline)하기로 결정할 수 있습니다.

Go에서 컴파일러는 [runtime/pprof](https://pkg.go.dev/runtime/pprof) 또는 [net/http/pprof](https://pkg.go.dev/net/http/pprof)와 같은 CPU pprof 프로파일을 입력 프로파일로 사용합니다.

Go 1.22 기준으로, 대표적인 Go 프로그램 세트에 대한 벤치마크 결과 PGO를 사용하여 빌드했을 때 성능이 약 2-14% 향상되는 것으로 나타났습니다.
향후 Go 버전에서 추가적인 최적화가 PGO를 활용함에 따라, 일반적으로 성능 향상 폭이 시간이 지남에 따라 증가할 것으로 기대합니다.

# 프로파일 수집 {#collecting-profiles}

Go 컴파일러는 PGO의 입력값으로 CPU pprof 프로파일을 기대합니다.
Go 런타임([runtime/pprof](https://pkg.go.dev/runtime/pprof) 및 [net/http/pprof](https://pkg.go.dev/net/http/pprof) 등)에서 생성된 프로파일은 컴파일러 입력으로 직접 사용할 수 있습니다.
다른 프로파일링 시스템의 프로파일을 사용하거나 변환하여 사용할 수도 있습니다. 자세한 내용은 [부록](#alternative-sources)을 참조하십시오.

최선의 결과를 얻으려면 프로파일이 애플리케이션의 실제 프로덕션 환경에서의 동작을 _대표_하는 것이 중요합니다.
대표성이 없는 프로파일을 사용하면 프로덕션 환경에서 개선 효과가 거의 없거나 전혀 없는 바이너리가 생성될 가능성이 큽니다.
따라서 프로덕션 환경에서 직접 프로파일을 수집하는 것이 권장되며, 이는 Go의 PGO가 설계된 주요 방식입니다.

일반적인 워크플로우는 다음과 같습니다:

1. 초기 바이너리를 빌드하고 릴리스합니다 (PGO 없이).
2. 프로덕션 환경에서 프로필을 수집합니다.
3. 업데이트된 바이너리를 릴리스할 때, 최신 소스에서 빌드하며 프로덕션 프로필을 제공합니다.
4. 2번 단계로 돌아갑니다 (GOTO 2).

Go PGO는 프로파일링된 애플리케이션 버전과 프로파일을 사용하여 빌드하는 버전 간의 불일치(skew)뿐만 아니라, 이미 최적화된 바이너리에서 수집한 프로파일로 빌드하는 경우에도 일반적으로 견고하게 동작합니다.
이러한 특성 덕분에 반복적인 라이프사이클이 가능해집니다.
이 워크플로우에 대한 자세한 내용은 [AutoFDO](#autofdo) 섹션을 참조하세요.

운영 환경에서 수집하는 것이 어렵거나 불가능한 경우(예: 최종 사용자에게 배포되는 커맨드라인 도구), 대표성 있는 벤치마크를 통해 수집하는 것도 가능합니다.
대표성 있는 벤치마크를 구성하는 것은 종종 매우 어려우며(애플리케이션이 진화함에 따라 대표성을 유지하는 것 또한 마찬가지입니다), 이 점에 유의하십시오.
특히, _마이크로벤치마크는 PGO 프로파일링에 적합하지 않은 경우가 많습니다_. 마이크로벤치마크는 애플리케이션의 아주 작은 부분만 실행하므로, 이를 전체 프로그램에 적용했을 때 얻을 수 있는 이득이 적기 때문입니다.

# PGO를 이용한 빌드 {#building}

빌드하는 표준 방식은 프로파일링 대상 바이너리의 메인 패키지 디렉토리에 `default.pgo`라는 파일 이름으로 pprof CPU 프로파일을 저장하는 것입니다.
기본적으로 `go build`는 `default.pgo` 파일을 자동으로 감지하여 PGO를 활성화합니다.

프로파일은 재현 가능하고(동시에 성능이 뛰어난!) 빌드에 중요한 입력값이므로, 이를 소스 저장소에 직접 커밋하는 것을 권장합니다.

프로파일을 소스와 함께 저장하면 소스를 가져오는 것 외에 프로파일을 얻기 위한 추가 단계가 필요 없으므로 빌드 경험이 단순해집니다.

더 복잡한 시나리오의 경우, `go build -pgo` 플래그를 통해 PGO 프로필 선택을 제어할 수 있습니다.
이 플래그의 기본값은 `-pgo=auto`이며, 앞서 설명한 `default.pgo` 동작 방식이 적용됩니다.
플래그를 `-pgo=off`로 설정하면 PGO 최적화가 완전히 비활성화됩니다.

`default.pgo`를 사용할 수 없는 경우(예: 하나의 바이너리에 대해 시나리오별로 서로 다른 프로파일이 필요한 경우, 소스와 함께 프로파일을 저장할 수 없는 경우 등), 사용할 프로파일의 경로를 직접 전달할 수 있습니다(예: `go build -pgo=/tmp/foo.pprof`).

_참고: `-pgo`에 전달된 경로는 모든 메인 패키지에 적용됩니다.
예를 들어, `go build -pgo=/tmp/foo.pprof ./cmd/foo ./cmd/bar`는 `foo.pprof`를 `foo`와 `bar` 두 바이너리 모두에 적용하며, 이는 대개 의도한 결과가 아닐 것입니다.
일반적으로 서로 다른 바이너리는 서로 다른 프로필을 가져야 하며, 각각 별도의 `go build` 호출을 통해 전달해야 합니다._

_참고: Go 1.21 이전 버전에서는 기본값이 `-pgo=off`입니다. PGO를 명시적으로 활성화해야 합니다._

# Notes {#notes}

## 운영 환경에서 대표 프로파일 수집하기

[프로파일 수집](#collecting-profiles)에서 설명한 바와 같이, 운영 환경은 애플리케이션의 대표적인 프로파일을 얻을 수 있는 가장 좋은 소스입니다.

가장 간단하게 시작하는 방법은 애플리케이션에 [net/http/pprof](https://pkg.go.dev/net/http/pprof)를 추가한 다음, 서비스의 임의 인스턴스에서 `/debug/pprof/profile?seconds=30`을 호출하는 것입니다.
이는 시작하기에 좋은 방법이지만, 다음과 같은 이유로 대표성이 떨어질 수 있습니다.

* 이 인스턴스는 평소에는 바쁘게 동작하더라도, 프로파일링되는 순간에는 아무런 작업도 수행하고 있지 않을 수 있습니다.

* 트래픽 패턴은 하루 동안 변할 수 있으며, 이에 따라 동작 또한 하루 동안 변할 수 있습니다.

* 인스턴스는 장시간 실행되는 작업(예: 작업 A를 5분 동안 수행한 후, 작업 B를 5분 동안 수행하는 등)을 실행할 수 있습니다.
  30초의 프로파일링으로는 단일 작업 유형만 포함될 가능성이 높습니다.

* 인스턴스가 요청을 공정하게 분배받지 못할 수 있습니다 (일부 인스턴스가 다른 인스턴스보다 특정 유형의 요청을 더 많이 받는 경우).

더욱 견고한 전략은 서로 다른 인스턴스에서 서로 다른 시간에 여러 프로필을 수집하여, 개별 인스턴스 프로필 간의 차이로 인한 영향을 제한하는 것입니다.
그 후 여러 프로필을 하나의 프로필로 [병합](#merging-profiles)하여 PGO에 사용할 수 있습니다.

많은 조직들이 이러한 방식의 플릿 전체 샘플링 프로파일링을 자동으로 수행하는 "지속적 프로파일링(continuous profiling)" 서비스를 운영하고 있으며, 이는 PGO를 위한 프로파일 소스로 활용될 수 있습니다.

## 프로필 병합 {#merging-profiles}

pprof 도구는 다음과 같이 여러 프로파일을 병합할 수 있습니다:

```
$ go tool pprof -proto a.pprof b.pprof > merged.pprof
```

이 병합은 프로파일의 wall duration(실제 경과 시간)과 관계없이 입력된 샘플들의 단순 합계로 처리됩니다.

그 결과, 애플리케이션의 짧은 시간 슬라이스를 프로파일링할 때(예: 무기한으로 실행되는 서버), 모든 프로파일이 동일한 wall duration을 갖도록(즉, 모든 프로파일이 30초 동안 수집되도록) 보장해야 할 가능성이 높습니다.

그렇지 않으면 wall duration이 더 긴 프로파일이 병합된 프로파일에서 과하게 반영됩니다.

## AutoFDO {#autofdo}

Go PGO는 “[AutoFDO](https://research.google/pubs/pub45290/)” 스타일의 워크플로우를 지원하도록 설계되었습니다.

[프로파일 수집](#collecting-profiles)에서 설명한 워크플로우를 더 자세히 살펴보겠습니다:

1. 초기 바이너리를 빌드하고 릴리스합니다 (PGO 없이).
2. 프로덕션 환경에서 프로필을 수집합니다.
3. 업데이트된 바이너리를 릴리스할 때, 최신 소스에서 빌드하고 프로덕션 프로필을 제공합니다.
4. 2단계로 돌아갑니다(GOTO 2).

겉으로는 단순해 보이지만, 여기서 주의 깊게 살펴봐야 할 몇 가지 중요한 속성들이 있습니다.

* 개발은 항상 진행 중이므로, 프로파일링된 바이너리 버전(2단계)의 소스 코드는 빌드되는 최신 소스 코드(3단계)와 약간 다를 가능성이 높습니다.
  Go PGO는 이러한 상황에서도 안정적으로 작동하도록 설계되었으며, 이를 _소스 안정성(source stability)_이라고 합니다.

* 이것은 폐쇄 루프(closed loop)입니다.
  즉, 첫 번째 반복 이후에는 프로파일링된 바이너리 버전이 이미 이전 반복에서 얻은 프로파일로 PGO 최적화가 적용된 상태입니다.
  Go PGO는 이러한 상황에서도 견고하게 작동하도록 설계되었으며, 이를 _반복 안정성(iterative stability)_이라고 부릅니다.

_소스 안정성(Source stability)_은 프로파일의 샘플을 컴파일 중인 소스와 매칭하는 휴리스틱을 사용하여 달성됩니다.
그 결과, 새로운 함수를 추가하는 것과 같은 소스 코드의 많은 변경 사항이 기존 코드 매칭에 영향을 주지 않습니다.
컴파일러가 변경된 코드를 매칭할 수 없는 경우 일부 최적화 기회를 잃게 되지만, 이는 _점진적 성능 저하(graceful degradation)_라는 점에 유의하십시오.
단일 함수가 매칭에 실패하면 최적화 기회를 잃을 수 있지만, 전반적인 PGO 이점은 보통 많은 함수에 걸쳐 분산되어 있습니다. 매칭 및 성능 저하에 대한 자세한 내용은 [소스 안정성](#source-stability) 섹션을 참조하십시오.

_반복 안정성(Iterative stability)_이란 연속적인 PGO 빌드에서 성능이 변동되는 주기(예: 빌드 #1은 빠르고, 빌드 #2는 느리고, 빌드 #3은 다시 빠른 현상 등)를 방지하는 것을 의미합니다.
우리는 CPU 프로파일을 사용하여 최적화 대상이 될 핫 함수(hot functions)를 식별합니다.
이론적으로, PGO를 통해 핫 함수의 속도가 매우 빨라지면 다음 프로파일에서는 더 이상 핫 함수로 나타나지 않아 최적화가 적용되지 않고, 결과적으로 다시 느려질 수 있습니다.
Go 컴파일러는 PGO 최적화에 보수적인 접근 방식을 취하며, 이를 통해 상당한 성능 변동을 방지할 수 있다고 믿습니다.
만약 이러한 종류의 불안정성을 발견하신다면, [go.dev/issue/new](/issue/new)에서 이슈를 제기해 주세요.

소스 안정성(source stability)과 반복적 안정성(iterative stability)이 결합되면, 첫 번째 단계에서 최적화되지 않은 빌드를 카나리로 프로파일링한 후 운영 환경을 위해 PGO로 다시 빌드하는 2단계 빌드 요구 사항이 제거됩니다(절대적인 최대 성능이 필요한 경우가 아니라면 말입니다).

## 소스 안정성 및 리팩터링 {#source-stability}

위에서 설명한 바와 같이, Go의 PGO는 이전 프로필의 샘플을 현재 소스 코드와 계속 매칭시키기 위해 최선의 노력(best-effort)을 기울입니다.
구체적으로, Go는 함수 내의 라인 오프셋(예: 함수 `foo`의 5번째 라인에서의 호출)을 사용합니다.

다음을 포함하여 일반적인 많은 변경 사항은 매칭을 깨뜨리지 않습니다:

* 핫 함수(hot function) 외부 파일의 변경 사항(함수 위 또는 아래에 코드를 추가하거나 변경하는 경우).

* 동일한 패키지 내의 다른 파일로 함수를 이동 (컴파일러는 소스 파일 이름을 완전히 무시합니다).

매칭을 중단시킬 수 있는 일부 변경 사항:

* 핫 함수(hot function) 내의 변경 사항 (라인 오프셋에 영향을 줄 수 있음).

* 함수(및/또는 메서드의 경우 타입)의 이름을 변경합니다 (심볼 이름이 변경됩니다).

* 함수를 다른 패키지로 이동 (심볼 이름 변경).

프로파일이 비교적 최근의 것이라면, 차이점은 아마도 소수의 핫 함수(hot functions)에만 영향을 미칠 것이며, 매칭에 실패한 함수에서 최적화 기회를 놓치더라도 그 영향은 제한적일 것입니다.

그럼에도 불구하고, 코드가 이전 형태로 다시 리팩토링되는 경우는 드물기 때문에 성능 저하는 시간이 지남에 따라 서서히 누적될 것입니다. 따라서 운영 환경과의 소스 스큐(source skew)를 제한하기 위해 정기적으로 새로운 프로파일을 수집하는 것이 중요합니다.

프로파일 매칭 성능이 크게 저하될 수 있는 한 가지 상황은 많은 함수 이름을 변경하거나 패키지 간에 함수를 이동시키는 대규모 리팩터링이 발생하는 경우입니다.
이 경우, 새로운 구조가 반영된 새로운 프로파일이 생성될 때까지 단기적인 성능 저하가 발생할 수 있습니다.

단순한 이름 변경(rote renames)의 경우, 이론적으로는 기존 프로필을 다시 작성하여 이전 심볼 이름을 새 이름으로 변경할 수 있습니다.
[github.com/google/pprof/profile](https://pkg.go.dev/github.com/google/pprof/profile)에는 pprof 프로필을 이러한 방식으로 다시 작성하는 데 필요한 프리미티브(primitives)가 포함되어 있지만, 작성 시점 기준으로 이를 위한 기성 도구(off-the-shelf tool)는 존재하지 않습니다.

## 새 코드의 성능

새로운 코드를 추가하거나 플래그 전환(flag flip)을 통해 새로운 코드 경로를 활성화하는 경우, 해당 코드는 첫 번째 빌드의 프로파일에 포함되지 않습니다. 따라서 새로운 코드가 반영된 새 프로파일이 수집될 때까지 PGO 최적화가 적용되지 않습니다.

새로운 코드의 롤아웃(rollout)을 평가할 때, 초기 릴리스 상태가 안정 상태(steady state)의 성능을 나타내지 않는다는 점을 유의하십시오.

# 자주 묻는 질문 (FAQ) {#faq}

## PGO로 Go 표준 라이브러리 패키지를 최적화하는 것이 가능한가요?

네.
Go의 PGO는 프로그램 전체에 적용됩니다.
표준 라이브러리 패키지를 포함한 모든 패키지는 잠재적인 프로필 가이드 최적화(profile-guided optimizations)를 고려하여 다시 빌드됩니다.

## PGO를 사용하여 의존성 모듈에 있는 패키지를 최적화하는 것이 가능한가요?

네.
Go의 PGO는 프로그램 전체에 적용됩니다.
종속성에 포함된 패키지를 포함하여 모든 패키지는 잠재적인 프로필 가이드 최적화를 고려하여 다시 빌드됩니다.
이는 애플리케이션이 종속성을 사용하는 고유한 방식이 해당 종속성에 적용되는 최적화에 영향을 미친다는 것을 의미합니다.

## 대표성이 없는 프로파일을 사용한 PGO가 PGO를 사용하지 않았을 때보다 프로그램을 더 느리게 만들 수 있나요?

그렇지 않아야 합니다.
프로덕션 동작을 대표하지 않는 프로필을 사용하면 애플리케이션의 콜드 파트(cold parts)에서 최적화가 이루어지겠지만, 핫 파트(hot parts)의 속도가 더 느려지지는 않아야 합니다.
만약 PGO를 비활성화했을 때보다 PGO를 적용했을 때 성능이 더 저하되는 프로그램을 발견하신다면, [go.dev/issue/new](/issue/new)에서 이슈를 제기해 주세요.

## 서로 다른 GOOS/GOARCH 빌드에 동일한 프로파일을 사용할 수 있나요?

아니요, 사용할 수 없습니다. `pprof` 프로파일은 특정 바이너리에 바인딩되어 있으며, 바이너리의 각 함수에 대응하는 주소를 기반으로 데이터를 저장합니다.

`GOOS` 또는 `GOARCH`를 변경하면 컴파일된 바이너리의 레이아웃과 함수 주소가 변경되므로, 한 플랫폼에서 생성된 프로파일을 다른 플랫폼의 바이너리에 적용하면 주소가 일치하지 않아 유효한 분석 결과를 얻을 수 없습니다.

각 플랫폼 조합(`GOOS`/`GOARCH`)에 대해 별도의 프로파일을 수집하고 분석해야 합니다.

네.
프로파일의 형식은 OS 및 아키텍처 구성에 관계없이 동일하므로, 서로 다른 구성 간에도 사용할 수 있습니다.
예를 들어, linux/arm64 바이너리에서 수집한 프로파일을 windows/amd64 빌드에서 사용할 수 있습니다.

그럼에도 불구하고, [위](#autofdo)에서 논의된 소스 안정성 주의 사항이 여기에도 동일하게 적용됩니다.
이러한 설정 간에 서로 다른 소스 코드는 최적화되지 않습니다.
대부분의 애플리케이션에서 코드의 대다수는 플랫폼 독립적이므로, 이러한 형태의 성능 저하는 제한적입니다.

구체적인 예로, `os` 패키지의 파일 처리 내부 구현은 Linux와 Windows에서 서로 다릅니다.
만약 Linux 프로파일에서 이러한 함수들이 hot-spot으로 지정된다면, Windows의 대응 함수들은 프로파일과 일치하지 않기 때문에 PGO 최적화가 적용되지 않습니다.

서로 다른 GOOS/GOARCH 빌드의 프로필을 병합할 수 있습니다. 그렇게 했을 때의 트레이드오프(trade-offs)는 다음 질문을 참조하십시오.

## 서로 다른 워크로드 유형에 사용되는 단일 바이너리를 어떻게 처리해야 합니까?

여기에는 명확한 선택지가 없습니다.
다양한 유형의 워크로드에 사용되는 단일 바이너리(예: 한 서비스에서는 읽기 중심적으로, 다른 서비스에서는 쓰기 중심적으로 사용되는 데이터베이스)는 서로 다른 핫 컴포넌트(hot components)를 가질 수 있으며, 이는 서로 다른 최적화의 이점을 얻습니다.

세 가지 옵션이 있습니다:

1. 워크로드별로 바이너리의 서로 다른 버전을 빌드합니다. 각 워크로드의 프로필을 사용하여 워크로드에 특화된 여러 버전의 바이너리를 빌드합니다.
   이렇게 하면 각 워크로드에 대해 최적의 성능을 제공할 수 있지만, 여러 바이너리와 프로필 소스를 관리해야 하므로 운영 복잡성이 증가할 수 있습니다.

2. “가장 중요한” 워크로드의 프로파일만 사용하여 단일 바이너리를 빌드하십시오: “가장 중요한” 워크로드(가장 큰 풋프린트를 가지거나 성능에 가장 민감한 워크로드)를 선택하고, 해당 워크로드의 프로파일만 사용하여 빌드하십시오.
   이렇게 하면 선택한 워크로드에 대해 최적의 성능을 제공하며, 워크로드 간에 공유되는 공통 코드에 대한 최적화를 통해 다른 워크로드에서도 어느 정도의 성능 향상을 기대할 수 있습니다.

3. 워크로드 간 프로필 병합: 각 워크로드에서 프로필을 가져와(전체 풋프린트로 가중치 부여) 이를 하나의 "플릿 전체(fleet-wide)" 프로필로 병합하고, 이를 통해 단일 공통 프로필을 빌드합니다.
   이는 모든 워크로드에 대해 적절한 성능 향상을 제공할 가능성이 높습니다.

## PGO가 빌드 시간에 어떤 영향을 미치나요?

PGO 빌드를 활성화하면 패키지 빌드 시간이 눈에 띄게 증가할 가능성이 높습니다.
가장 두드러진 점은 PGO 프로파일이 바이너리 내의 모든 패키지에 적용된다는 것이며, 이는 프로파일을 처음 사용할 때 의존성 그래프에 있는 모든 패키지를 다시 빌드해야 함을 의미합니다.
이러한 빌드는 다른 빌드와 마찬가지로 캐시되므로, 동일한 프로파일을 사용하는 이후의 증분 빌드(incremental builds)에서는 전체 재빌드가 필요하지 않습니다.

빌드 시간이 과도하게 증가하는 현상을 겪으신다면, [go.dev/issue/new](/issue/new)에서 이슈를 제기해 주세요.

## PGO가 바이너리 크기에 어떤 영향을 미치나요?

PGO는 추가적인 함수 인라이닝(function inlining)으로 인해 바이너리 크기가 약간 더 커질 수 있습니다.

# 부록: 대체 프로필 소스 {#alternative-sources}

Go 런타임(예: [runtime/pprof](https://pkg.go.dev/runtime/pprof) 등)에 의해 생성된 CPU 프로파일은 이미 PGO 입력값으로 직접 사용할 수 있는 올바른 형식을 갖추고 있습니다.
하지만 조직에 따라 선호하는 대체 툴링(예: Linux perf)이 있거나, Go PGO와 함께 사용하려는 기존의 플릿 단위(fleet-wide) 지속적 프로파일링 시스템이 있을 수 있습니다.

대체 소스에서 가져온 프로파일을 [pprof 형식](https://github.com/google/pprof/tree/main/proto)으로 변환한다면 Go PGO와 함께 사용할 수 있으며, 이때 다음의 일반적인 요구 사항을 충족해야 합니다.

* 샘플 인덱스 중 하나는 type/unit이 "samples"/"count" 또는 "cpu"/"nanoseconds"여야 합니다.

* 샘플은 샘플 위치에서의 CPU 시간 샘플을 나타내야 합니다.

* 프로파일은 심볼화되어 있어야 합니다 ([Function.name](https://github.com/google/pprof/blob/76d1ae5aea2b3f738f2058d17533b747a1a5cd01/proto/profile.proto#L208)이 설정되어 있어야 함).

* 샘플에는 인라인 함수(inlined functions)에 대한 스택 프레임이 포함되어야 합니다.
  인라인 함수가 누락되면, Go는 반복 안정성(iterative stability)을 유지할 수 없습니다.

* [Function.start_line](https://github.com/google/pprof/blob/76d1ae5aea2b3f738f2058d17533b747a1a5cd01/proto/profile.proto#L215)이 설정되어야 합니다.
  이 값은 함수의 시작 라인 번호입니다.
  즉, `func` 키워드가 포함된 라인을 의미합니다.
  Go 컴파일러는 이 필드를 사용하여 샘플의 라인 오프셋(`Location.Line.line - Function.start_line`)을 계산합니다.
  **기존의 많은 pprof 컨버터들이 이 필드를 생략한다는 점에 유의하십시오.**

_참고: Go 1.21 이전 버전의 DWARF 메타데이터에는 함수 시작 라인(`DW_AT_decl_line`)이 생략되어 있어, 도구가 시작 라인을 결정하는 데 어려움이 있을 수 있습니다._

특정 서드파티 도구의 PGO 호환성에 대한 추가 정보는 Go Wiki의 [PGO Tools](/wiki/PGO-Tools) 페이지를 참조하십시오.
