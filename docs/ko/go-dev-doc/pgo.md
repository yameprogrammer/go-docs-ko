# 개요 {#overview}

프로파일 가이드 최적화 (PGO), 또는 피드백 지향 최적화 (FDO)는 컴파일러 최적화 기술로, 애플리케이션의 대표적인 실행 결과 (프로파일)를 컴파일러에 피드백으로 제공하여, 컴파일러가 해당 정보를 사용하여 더 정교한 최적화 결정을 내립니다.

예를 들어, 컴파일러는 프로파일이 자주 호출되는 함수를 더욱 적극적으로 인라인하도록 결정할 수 있습니다.

Go에서 컴파일러는 `runtime/pprof` 또는 `net/http/pprof`에서 생성된 CPU pprof 프로파일을 입력 프로파일로 사용합니다.

Go 1.22 기준으로, 대표적인 Go 프로그램에 대한 성능 테스트 결과, PGO를 사용하여 빌드하면 성능이 약 2-14% 향상됩니다.

향후 Go의 버전에서 추가적인 최적화가 PGO를 활용함에 따라, 성능 향상이 점진적으로 증가할 것으로 예상됩니다.

# 사용자 프로필 수집 {#collecting-profiles}

## 설명
이 섹션에서는 사용자 프로필을 수집하는 방법에 대한 설명을 제공합니다.

Go 컴파일러는 PGO에 대한 입력으로 CPU pprof 프로필을 기대합니다.
[runtime/pprof](https://pkg.go.dev/runtime/pprof) 및 [net/http/pprof](https://pkg.go.dev/net/http/pprof)에서 생성된 Go 런타임에 의해 생성된 프로필은 직접 컴파일러 입력으로 사용할 수 있습니다.
또한 다른 프로파일링 시스템의 프로필을 사용하거나 변환하는 것도 가능합니다. 자세한 내용은 [부록](#alternative-sources)을 참조하십시오.

최적의 결과를 얻으려면 프로파일이 실제 애플리케이션의 프로덕션 환경에서의 동작을 _대표_해야 합니다.

대표성이 없는 프로파일을 사용하면 프로덕션 환경에서 거의 개선이 없을 가능성이 높습니다.
따라서 프로덕션 환경에서 직접 프로파일을 수집하는 것이 권장되며, 이는 Go의 PGO가 설계된 주요 방법입니다.

일반적인 워크플로우는 다음과 같습니다:

1. 초기 바이너리를 빌드하고 배포 (PGO 미사용).
2. 프로덕션 환경에서 프로파일을 수집.
3. 업데이트된 바이너리를 배포할 때, 최신 소스에서 빌드하고 프로덕션 프로파일을 제공.
4. 2번으로 돌아감.

Go PGO는 프로파일링된 애플리케이션 버전과 프로필을 사용하여 빌드된 버전 간의 불일치, 그리고 이미 최적화된 바이너리에서 수집된 프로필을 사용하여 빌드하는 데 일반적으로 견고합니다.
이것이 이러한 반복적인 라이프사이클을 가능하게 합니다.
이 워크플로우에 대한 추가 세부 정보는 [AutoFDO](#autofdo) 섹션을 참조하세요.

만약 생산 환경에서 수집하기 어렵거나 불가능한 경우 (예: 최종 사용자에게 배포된 명령줄 도구)에는 대표적인 벤치마크에서 수집하는 것도 가능합니다.
참고로, 대표적인 벤치마크를 구성하는 것은 종종 매우 어렵습니다 (특히 애플리케이션이 진화함에 따라 벤치마크를 대표적으로 유지하는 것도 어렵습니다).
특히, _마이크로 벤치마크는 일반적으로 PGO 프로파일링에 적합하지 않습니다. 왜냐하면 이들은 애플리케이션의 작은 부분만을 실행하기 때문이며, 전체 프로그램에 적용하면 작은 성능 향상만을 가져옵니다.

# PGO를 사용하여 빌드하기 {#building}

표준적인 빌드 방식은 프로파일링된 바이너리의 메인 패키지 디렉토리에 `default.pgo`라는 이름으로 pprof CPU 프로파일을 저장하는 것입니다.

기본적으로 `go build`는 `default.pgo` 파일을 자동으로 감지하고 PGO를 활성화합니다.

소스 저장소에서 직접 프로필을 커밋하는 것이 권장됩니다. 프로필은 재현 가능하고(그리고 효율적인!) 빌드에 필요한 입력이기 때문입니다.

소스와 함께 저장하면, 소스를 가져지는 것 외에 추가적인 단계 없이 프로필을 얻을 수 있어 빌드 경험이 단순화됩니다.

더 복잡한 시나리오의 경우, `go build -pgo` 플래그는 PGO 프로필 선택을 제어합니다.
이 플래그는 위에서 설명한 `default.pgo` 동작에 대해 기본값으로 `-pgo=auto`를 사용합니다.
플래그를 `-pgo=off`로 설정하면 PGO 최적화를 완전히 비활성화합니다.

만약 `default.pgo`를 사용할 수 없는 경우 (예: 하나의 바이너리에서 서로 다른 시나리오에 대한 프로필, 소스와 함께 프로필을 저장할 수 없는 경우 등), 직접 사용할 프로필의 경로를 지정할 수 있습니다 (예: `go build -pgo=/tmp/foo.pprof`).

_참고: `-pgo`에 전달된 경로는 모든 메인 패키지에 적용됩니다.
예: `go build -pgo=/tmp/foo.pprof ./cmd/foo ./cmd/bar`는 `foo.pprof`을 `foo` 및 `bar` 바이너리에 모두 적용하며, 이는 일반적으로 원하는 결과가 아닙니다.
일반적으로 다른 바이너리는 각각 다른 프로필을 사용해야 하며, 별도의 `go build` 호출을 통해 전달해야 합니다._

_참고: Go 1.21 이전 버전에서는 기본 설정이 `-pgo=off`입니다. PGO는 명시적으로 활성화해야 합니다._

# 참고 사항 {#notes}

## 운영 환경에서 대표적인 사용자 프로필 수집

## 목표

*   운영 환경에서 사용되는 대표적인 사용자 프로필을 수집합니다.
*   수집된 프로필 정보를 분석하여 사용자 행동 패턴을 파악합니다.
*   파악된 사용자 행동 패턴을 기반으로 시스템 개선 및 개인화된 서비스를 제공합니다.

## 방법

1.  **사용자 프로필 수집**: 운영 환경에서 사용자의 활동 데이터를 수집합니다. (예: 로그인 정보, 사용 패턴, 설정 정보 등)
2.  **데이터 분석**: 수집된 데이터를 분석하여 사용자 행동 패턴을 파악합니다. (예: 인기 기능 사용 빈도, 특정 시간대 사용량, 특정 콘텐츠 소비 패턴 등)
3.  **대표적인 프로필 정의**: 분석 결과를 바탕으로 대표적인 사용자 프로필을 정의합니다. (예: "초보 사용자", "심층 사용자", "주 사용 콘텐츠", "특정 기능 선호 사용자" 등)
4.  **프로필 정보 관리**: 정의된 프로필 정보를 체계적으로 관리합니다. (예: 프로필 정의, 사용자 매핑, 데이터 업데이트 등)

당신의 프로덕션 환경은 애플리케이션을 대표하는 프로필을 수집하는 데 가장 좋은 출처입니다. [프로필 수집](#collecting-profiles)에서 설명한 바와 같습니다.

가장 간단한 방법은 [net/http/pprof](https://pkg.go.dev/net/http/pprof)을 애플리케이션에 추가한 다음, 서비스의 임의의 인스턴스에서 `/debug/pprof/profile?seconds=30`를 가져오는 것입니다.

이것은 시작하는 좋은 방법이지만, 이 방법이 대표성을 덜 반영할 수도 있습니다:

* 이 인스턴스는 프로파일링될 때 실제로 아무 작업도 수행하지 않을 수도 있습니다. 일반적으로는 매우 바쁘게 작동합니다.

* 일중 교통 패턴이 변동될 수 있으며, 이는 일중 행동 변화를 유발할 수 있습니다.

* 인스턴스는 장시간 실행되는 작업(예: 작업 A를 5분 동안, 그 다음 작업 B를 5분 동안 등)을 수행할 수 있습니다.
  30초 프로파일은 일반적으로 단일 작업 유형만 캡처합니다.

* 인스턴스가 공정하게 요청을 받지 못할 수 있습니다 (일부 인스턴스는 다른 인스턴스보다 특정 유형의 요청을 더 많이 받습니다).

더 강력한 전략은 서로 다른 시간, 서로 다른 인스턴스에서 여러 프로필을 수집하여 개별 인스턴스 프로필 간의 차이의 영향을 최소화하는 것입니다.

그런 다음 여러 프로필을 단일 프로필로 [병합](#merging-profiles)하여 PGO에서 사용할 수 있습니다.

많은 조직은 이러한 종류의 전체 시스템 샘플링 프로파일링을 자동으로 수행하는 "지속적인 프로파일링" 서비스를 운영합니다. 이러한 프로파일링 결과는 PGO에 사용될 수 있습니다.

## 프로필 병합하기 {#merging-profiles}

`pprof` 도구를 사용하여 여러 프로파일을 다음과 같이 병합할 수 있습니다:

```
$ go tool pprof -proto a.pprof b.pprof > merged.pprof
```

이 병합은 입력을 기반으로 샘플의 단순한 합산으로 효과적으로 작동하며, 프로필의 벽 시간은 관계없이 동일합니다.
따라서, 애플리케이션의 작은 시간 슬라이스를 프로파일링하는 경우 (예: 무한 실행되는 서버), 모든 프로필이 동일한 벽 시간을 갖도록 하는 것이 좋습니다 (즉, 모든 프로필이 30초 동안 수집).
그렇지 않으면, 더 긴 벽 시간을 갖는 프로필이 병합된 프로필에서 과도하게 나타날 수 있습니다.

## AutoFDO

Go PGO는 "[AutoFDO](https://research.google/pubs/pub45290/)" 스타일의 워크플로우를 지원하도록 설계되었습니다.

자세히 살펴보기 위해, "[수집 프로필](#collecting-profiles) 섹션에 설명된 워크플로우를 살펴보겠습니다:"

1. 초기 바이너리(PGO 없이)를 빌드하고 배포합니다.
2. 프로덕션 환경에서 프로파일을 수집합니다.
3. 업데이트된 바이너리를 배포할 때, 최신 소스에서 빌드하고 프로덕션 프로파일을 제공합니다.
4. 2단계로 이동

이것은 겉보기에는 간단해 보이지만, 몇 가지 중요한 속성을 고려해야 합니다:

* 개발은 지속적으로 진행되므로, 프로파일링된 바이너리의 소스 코드 (2단계)는 빌드되는 최신 소스 코드 (3단계)와 약간 다를 수 있습니다.
  Go PGO는 이러한 상황을 견딜 수 있도록 설계되었으며, 이를 _소스 안정성_이라고 합니다.

* 이것은 폐쇄 루프입니다.
  즉, 첫 번째 반복 이후 프로파일링된 바이너리는 이전 반복의 프로파일을 사용하여 이미 PGO 최적화되어 있습니다.
  Go PGO 또한 이러한 상황에 강건하도록 설계되었으며, 이를 "반복적 안정성"이라고 합니다.

_소스 안정성_은 프로파일에서 샘플을 컴파일된 소스와 일치시키는 데 사용되는 휴리스틱을 통해 달성됩니다.
따라서 소스 코드에 대한 변경 사항, 예를 들어 새 함수를 추가하는 경우, 기존 코드와 일치하는 데 영향을 미치지 않습니다.
컴파일러가 변경된 코드를 일치시킬 수 없는 경우 일부 최적화가 손실되지만, 이는 _점진적 성능 저하_라고 합니다.
단일 함수가 일치하지 못하면 최적화 기회를 잃을 수 있지만, 전반적인 PGO의 이점은 일반적으로 여러 함수에 걸쳐 분산됩니다. 일치 및 성능 저하에 대한 자세한 내용은 [소스 안정성](#source-stability) 섹션을 참조하십시오.

_반복적 안정성_이란 연속적인 PGO 빌드에서 변동적인 성능 순환을 방지하는 것입니다 (예: 빌드 #1은 빠르고, 빌드 #2는 느리고, 빌드 #3은 빠르고, 등).
우리는 CPU 프로필을 사용하여 최적화할 핫한 함수를 식별합니다.
이론적으로, PGO를 통해 핫한 함수는 너무 빠르게 속도를 향상시켜 다음 프로필에서는 더 이상 핫하지 않고 최적화되지 않아 다시 느려질 수 있습니다.
Go 컴파일러는 보수적인 접근 방식을 사용하여 PGO 최적화를 수행하며, 이는 상당한 변동성을 방지한다고 믿습니다.
만약 이러한 불안정성을 관찰하는 경우, [go.dev/issue/new](/issue/new)에 문제를 제기해 주세요.

함께, 소스 코드와 반복적인 안정성은 두 단계 빌드에 대한 필요성을 제거합니다. 즉, 첫 번째 빌드 (최적화되지 않음)를 "캐노"로 프로파일링하고, 생산 환경에서는 PGO를 사용하여 다시 빌드하는 방식이 필요하지 않습니다 (단, 절대적인 최고의 성능이 필요할 경우에만).

## 소스 안정성과 리팩토링 {#source-stability}

위와 같이 설명된 바와 같이, Go의 PGO는 이전 프로필의 샘플과의 일치를 시도하여 현재 소스 코드와 매칭합니다.
구체적으로, Go는 함수 내의 라인 오프셋(예: 함수 foo의 5번째 라인 호출)을 사용합니다.

다음과 같은 일반적인 변경 사항은 일치성을 유지합니다:

* 파일 내의 핫 함수 외부에서 변경 (핫 함수의 위 또는 아래에 코드를 추가/변경)

* 동일 패키지 내의 함수를 다른 파일로 이동하는 경우 (컴파일러는 소스 파일 이름을 무시합니다).

다음 중 일치에 영향을 줄 수 있는 변경 사항:

* 핫 함수 내에서의 변경 (줄 오프셋에 영향을 줄 수 있음).

* 함수 (및/또는 메서드용 타입)의 이름 변경 (기호 이름 변경)

* 함수를 다른 패키지로 이동 (기호 이름 변경)

만약 프로필이 비교적 최신이라면, 차이는 주로 몇 가지 핵심 기능에만 영향을 미칠 가능성이 높으며, 일치하지 않는 함수에서 놓친 최적화의 영향을 제한합니다.

하지만 코드의 재구성이 거의 이루어지지 않으므로, 시간이 지남에 따라 성능 저하가 점진적으로 누적될 수 있습니다. 따라서 프로덕션 환경에서의 원본 코드와의 차이를 최소화하기 위해 새로운 프로필을 정기적으로 수집하는 것이 중요합니다.

하나의 경우로, 프로필 매칭이 크게 저하될 수 있는 상황은 대규모 리팩터링으로 인해 많은 함수를 이름이 변경하거나 다른 패키지로 이동시키는 경우입니다.

이 경우, 새로운 구조가 나타날 때까지 일시적인 성능 저하가 발생할 수 있습니다.

단순 이름 변경의 경우, 기존 프로파일을 수정하여 기존 심볼 이름을 새 이름으로 변경할 수 있습니다.
[github.com/google/pprof/profile](https://pkg.go.dev/github.com/google/pprof/profile)에는 프로파일을 이 방식으로 수정하는 데 필요한 기본 구성 요소가 포함되어 있지만, 현재로서는 이러한 기능을 제공하는 상용 도구는 없습니다.

## 새로운 코드의 성능

| 항목 | 설명 |
|---|---|
| CPU 사용률 | 평균 60% |
| 메모리 사용률 | 평균 40% |
| 응답 시간 | 평균 0.5초 |

새로운 코드 또는 플래그 변경으로 활성화된 새로운 코드 경로를 추가할 때, 해당 코드는 첫 번째 빌드에서는 프로필에 나타나지 않으므로 PGO 최적화를 받지 못합니다. 새로운 코드를 반영한 새로운 프로필이 수집될 때까지 최적화를 받지 않습니다.

새로운 코드를 배포할 때 성능을 평가할 때, 초기 릴리스가 안정적인 성능을 나타내지 않을 수 있다는 점을 염두에 두십시오.

## Go 표준 라이브러리 패키지를 PGO로 최적화할 수 있나요?

네.

Go에서 PGO는 전체 프로그램에 적용됩니다.
모든 패키지는 프로파일 가이드 최적화를 고려하여 다시 빌드됩니다. 여기에는 표준 라이브러리 패키지도 포함됩니다.

## PGO를 사용하여 상호 의존적인 모듈의 패키지 최적화는 가능한가?

네.

Go에서 PGO는 전체 프로그램에 적용됩니다.
모든 패키지는 잠재적인 프로파일 기반 최적화를 고려하여 다시 빌드됩니다. 여기에는 종속성에 있는 패키지도 포함됩니다.
이는 애플리케이션이 종속성을 사용하는 고유한 방식이 해당 종속성에 적용되는 최적화에 영향을 미친다는 것을 의미합니다.

## PGO를 사용하여 대표성이 없는 프로필을 사용하면 프로그램이 더 느려질까요?

이는 프로덕션 환경에서의 실제 동작을 제대로 반영하지 않는 프로파일이, 애플리케이션의 일부 영역(콜드 부분)에서는 최적화를 수행하지만, 다른 영역(핫 부분)의 성능을 저하시키는 것을 방지해야 합니다.

PGO(프로그램 실행 시 최적화)를 수행했지만, PGO를 비활성화했을 때보다 성능이 더 나빠지는 경우를 발견하면, [go.dev/issue/new](/issue/new)에 이슈를 제기해 주세요.

## 다른 GOOS/GOARCH 빌드에 동일한 프로필을 사용할 수 있나요?

예.

프로파일의 형식은 OS 및 아키텍처 구성에 관계없이 동일하므로, 서로 다른 구성에서 사용할 수 있습니다.
예를 들어, Linux/arm64 바이너리에서 수집된 프로파일은 Windows/amd64 빌드에 사용될 수 있습니다.

그럼에도 불구하고, 위에서 논의된 [소스 안정성 관련 사항](#autofdo)은 여기에도 적용됩니다.

이러한 구성 간에 다른 소스 코드는 최적화되지 않습니다.

대부분의 애플리케이션에서, 코드의 대부분은 플랫폼 독립적이므로, 이러한 문제가 발생할 가능성은 매우 낮습니다.

예를 들어, `os` 패키지의 파일 처리 내부 동작은 Linux와 Windows에서 다릅니다.
만약 Linux 프로파일에서 이러한 함수가 활성화되어 있다면, Windows의 해당 함수는 PGO 최적화를 받지 못합니다. 왜냐하면 프로파일이 일치하지 않기 때문입니다.

여러 GOOS/GOARCH 빌드의 프로필을 병합할 수 있습니다. 이를 수행하는 것의 장단점을 다음 질문에서 확인하십시오.

## 다양한 워크로드 유형에 사용되는 단일 바이너리를 어떻게 처리해야 할까요?

여기에는 명확한 선택이 없습니다.
단일 바이너리가 다양한 유형의 워크로드(예: 한 서비스에서 읽기 집중적으로 사용되고 다른 서비스에서는 쓰기 집중적으로 사용되는 데이터베이스)에 사용될 때, 각 워크로드에는 서로 다른 "핫"한 구성 요소가 있을 수 있으며, 이러한 구성 요소는 서로 다른 최적화의 이점을 얻을 수 있습니다.

다음 세 가지 옵션이 있습니다:

1. 각 워크로드에 대해 바이너리의 다양한 버전을 빌드합니다: 각 워크로드의 프로파일을 사용하여 바이너리의 여러 워크로드별 빌드를 만듭니다.
   이렇게 하면 각 워크로드에 대해 최상의 성능을 제공하지만, 여러 바이너리와 프로파일 소스를 관리하는 데 운영상의 복잡성을 추가할 수 있습니다.

2. "가장 중요한" 워크로드만 사용하여 단일 실행 파일 만들기: 가장 중요한 워크로드(가장 큰 크기, 성능에 민감한 워크로드)를 선택하고 해당 워크로드의 프로필만 사용하여 빌드합니다.
   이렇게 하면 선택된 워크로드에 대해 최상의 성능을 제공하며, 워크로드 간에 공유되는 공통 코드에 대한 최적화를 통해 다른 워크로드에도 미미한 성능 향상을 얻을 수 있습니다.

3. 워크로드별 프로필 병합: 각 워크로드(총 사용량을 기준으로 가중치 부여)의 프로필을 가져와 하나의 "전체 워크로드" 프로필로 병합합니다. 이 프로필은 단일 공통 프로필을 구축하는 데 사용됩니다.
   이는 모든 워크로드에 대해 상당한 성능 향상을 제공할 가능성이 있습니다.

## PGO가 빌드 시간을 어떻게 변경하는가?

PGO(Profile-Guided Optimization)는 빌드 시간을 증가시킬 수 있습니다. 그 이유는 다음과 같습니다.

*   **프로파일 생성:** PGO는 먼저 실행 프로파일을 생성해야 합니다. 이 단계에는 프로그램의 실행을 모니터링하고, 성능 병목 지점을 식별하는 작업이 포함됩니다. 이 과정은 상당한 시간이 소요될 수 있습니다.
*   **컴파일 및 최적화:** 생성된 프로파일을 사용하여 컴파일러는 코드를 다시 컴파일하고, 병목 지점을 개선하기 위한 최적화를 수행합니다. 이 단계 역시 시간이 오래 걸릴 수 있습니다.
*   **빌드 프로세스 복잡성 증가:** PGO를 사용하면 빌드 프로세스가 더 복잡해집니다. 컴파일러는 프로파일 정보를 고려해야 하므로, 추가적인 단계와 시간이 필요합니다.

따라서 PGO를 사용하면 빌드 시간이 크게 증가할 수 있습니다. 하지만, 궁극적으로 얻을 수 있는 성능 향상 효과는 이러한 시간 증가를 상쇄할 수 있습니다.

PGO 빌드 활성화는 패키지 빌드 시간에서 측정 가능한 증가를 초래할 수 있습니다.
이 중 가장 두드러지는 부분은 PGO 프로필이 바이너리에 있는 모든 패키지에 적용된다는 것입니다. 즉, 프로필을 처음 사용하는 경우, 의존성 그래프 내의 모든 패키지를 다시 빌드해야 합니다.
이 빌드는 다른 빌드와 마찬가지로 캐시됩니다. 따라서 동일한 프로필을 사용하여 후속의 점진적인 빌드를 수행할 때는 전체 재빌드가 필요하지 않습니다.

만약 빌드 시간이 급격하게 증가하는 경우, [go.dev/issue/new](/issue/new)에 이슈를 제출해 주세요.

## PGO가 바이너리 크기에 미치는 영향은 무엇인가?

PGO(Profile-Guided Optimization)가 바이너리 크기에 미치는 영향을 설명합니다.

PGO는 추가적인 함수 인라이닝으로 인해 약간 더 큰 바이너리를 생성할 수 있습니다.

# 부록: 대체 프로필 소스 {#alternative-sources}

CPU 프로필은 Go 런타임 (예: [runtime/pprof](https://pkg.go.dev/runtime/pprof) 등을 통해 생성됨)이 이미 PGO 입력으로 직접 사용하기에 적합한 형식입니다.
그러나 조직은 자체적으로 선호하는 도구 (예: Linux perf) 또는 기존의 전체 시스템 수준의 지속적인 프로파일링 시스템을 사용하고 싶을 수 있으며, 이를 Go PGO와 함께 사용하고 싶을 수 있습니다.

대체 소스에서 가져온 프로필은 [pprof 형식](https://github.com/google/pprof/tree/main/proto)으로 변환된 경우, Go PGO에서 사용할 수 있습니다. 단, 다음 일반적인 요구 사항을 충족해야 합니다:

* 샘플 인덱스 중 하나는 "type/unit"이 "samples"/"count" 또는 "cpu"/"nanoseconds"이어야 합니다.

* 샘플은 CPU 시간을 나타내는 샘플이어야 합니다.

* 프로필은 반드시 기호로 표시되어야 합니다 ([Function.name](https://github.com/google/pprof/blob/76d1ae5aea2b3f738f2058d17533b747a1a5cd01/proto/profile.proto#L208)를 설정해야 합니다).

* 샘플에는 인라인 함수에 대한 스택 프레임을 포함해야 합니다.
  인라인 함수가 누락되면 Go는 반복적 안정성을 유지할 수 없습니다.

* [Function.start_line](https://github.com/google/pprof/blob/76d1ae5aea2b3f738f2058d17533b747a1a5cd01/proto/profile.proto#L215)을 설정해야 합니다.
  이것은 함수의 시작 라인 번호입니다.
  즉, `func` 키워드가 포함된 라인입니다.
  Go 컴파일러는 이 필드를 사용하여 샘플의 라인 오프셋을 계산합니다 (`Location.Line.line - Function.start_line`).
  **참고: 많은 기존 pprof 변환기는 이 필드를 생략합니다.**

_참고: Go 1.21 이전에는 DWARF 메타데이터에서 함수 시작 라인(`DW_AT_decl_line`)이 누락되어, 도구가 시작 라인을 결정하는 데 어려움을 겪을 수 있습니다._

[PGO Tools](/wiki/PGO-Tools) 페이지에서 특정 타사 도구의 PGO 호환성에 대한 추가 정보를 확인하세요.
